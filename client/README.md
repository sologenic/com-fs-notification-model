# client

The package provides a wrapper to include the grpc service in your application.

## Start the service

The client is self initializing. For this it requires the following environment variable:

- `NOTIFICATION_STORE` - The host of the service. Host is in the format `host:port`

If the client is included and the env variable is not set, the client panics.

## Identification of notifications to prevent duplication of messages

The sender is responsible for ensuring a correct (unique) key. The model provides the following field for this:

- Key

The `Update` call uses the key with the provided content to **persist/update** the notification. So it **overwrites** the existing notification.
The `Persist` call checks if the key exists and if it does, it does not persist the notification.
In case control of the update/persist is required in the client itself, there is also an `Exists` call to check if the key exists.

The key generation logic is encapsulated in the client package with several helper functions:

1. Subscription notification: NotificationType + ID + Unique reference 

This allows for the usage of the fields like collectionID, reference, TransactionID, etc (unique reference) as retrieved from the ledger to generate the key unique to the given usage (NotificationType).

The client function for this is `SubscriptionKey`.

Example:
Collection ABC has an update. This update will have a transactionID.
A correct unique key to be used here would be:
ID + TransactionID + Type => `collectionID` + `transactionID` +`Collection`
In which the actual type will be the numeric representation of the type.

2. Admin style broadcast: NotificationType + Timestamp

An admin style notification is unique by design as in that the messsage is not from an automated source. The responsibility is on the sender to prevent duplicates. If the notificationID is present, this will be used to uniquify the message. If not a timestamp (unix nanos) is generated by the client function `AdminKey` and set to the notificationID field.

3. Type + ID + Reference + AccountID

There are automated processes sending messages to accounts. This needs to be kept unqieu by using the same reference as in point 1, however by now adding the accountID to the key, it has become identifiable to the account and duplicates can be prevented.

The function call for this is `AccountKey`.

4. Direct to account message (non automated): NotificationType + Timestamp + AccountID

It is possible to send messages to individual accounts. These could be comments, or just internal communication like verification messages.
Since this is a more open category where notificationType could just be "message", a more generic unique key is generated by the client function `DirectKey`.
This key generation generates a notificationID if not provided and will set that notificationID.

### Why optional notificationID generation?

The key functions provided a scenario defined key mechanism. If however a messsage is retrieved and the key function would be called again, the goal is that the key is immutable by the key functions itself (e.g. prevent a programming error).
If the key would have to be changed, this would be a very conscious decision of the developer.
